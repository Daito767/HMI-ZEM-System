# OPC UA — what the PLC publishes and how the cell is drawn

For writing the HMI. **This file is enough**: you do not need to open the project
and you do not need to read the ST code to build the interface. If you also want
context about the stand, `HANDOFF.md` is next to it.

Source: `Software v13.Device.Application.xml`, generated by Symbol Configuration
(`SupportOPCUA` on), checked **12.08.2026 09:20**. If anyone changes the symbol
selection again, that file is the truth, not this document; it is rewritten only
on code generation, not on build.

**755 variables** published, under five roots: `Main`, `HMI`, `IOs`,
`GVL_Diag`, `GVL_Config`. The names are the ones in the tables below; the exact
browse path differs from client to client — look for `Application`, then the root.

The selection is made **entirely from the Symbol Configuration dialog**. There
are no `{attribute 'symbol'}` pragmas in the source; there was an attempt, and it
was removed, because the pragma and the tick box are two sources of truth that
fight each other (the pragma gives the access ceiling, the tick box gives the
configured access, and the dialog marks red any `%Q` output that exceeds them).

> **509 of the 755 are writable.** Far more than the HMI needs.
> Read §5 before binding anything: there are a few the interface **must not**
> write, even though it can.


---

## 1. The model, in three sentences

The cell has **three columns** holding pallets: `-1` left, `0` the belt,
`1` right. Each column is a queue of pallets; **index 0 is at the front**, that is
the position the arm reaches. The storage feeds column 0 from the back, the belt
brings them to the front, the arm moves them between columns.

There are **two separate layers**: `Pool` holds the identity and contents of a
pallet, `Rows` holds the position. A queue holds `VirtualId`s (numbers), not
pallets — so a pallet carries its contents wherever it is moved. `VirtualId` is
the index into `Pool`; **that is the identity**, not `RealId` (there can be
pallets with no RFID or with the same id).

The arm has two effectors and one field for each: `InGripper` (which pallet it
holds, `-1` = empty) and `InVacuum` (which object it holds, `Missing` = empty).

## 2. All the variables

### 2.1 `Main` — commands and sequence state

| variable | type | access | what it is |
|---|---|---|---|
| `Main.StartCommand` | BOOL | **RW** | Start button. **This is the correct input** for starting |
| `Main.ResetCommand` | BOOL | **RW** | Reset button |
| `Main.PauseCommand` | BOOL | **RW** | Pause button (stops immediately) |
| `Main.EndStepPauseCommand` | BOOL | **RW** | pause at the end of the current step |
| `Main.Run` | BOOL | R | the cell is running. **State, not a command** — which is why it is read-only |
| `Main.ResetStarted` | BOOL | R | a reset is under way; display "resetting", not "stopped" |
| `Main.MainStep` | INT | R | the step of the main sequence, for live progress |
| `Main.ConfirmCycleEnd` | BOOL | **RW** | declared, but no code reads it. Do not use it |
| `Main.HaltStep` | INT | **RW** | the step of the last halt. It overlaps `Diag.Last.Step`; **do not write** |
| `Main.PalletDropRegion` | INT | **RW** | a task variable, written by `MainTask`. **Do not write** — you would be fighting the sequence |
| `Main.ObjectPriorities[0..9]` | INT | R | declared, no code reads it |
| `Main.ValueFromRFID` | INT | R | a dead declaration in `Main` (the live one is `HMI.ValueFromRFID`, also dead) |
| `Main.DropObjectPolicyTable[0..9]` | INT | **RW** | policy per colour: `0` leave on the pallet, `1` drop left, `2` drop right. Indexed by `ENUM_ObjectType` |
| `Main.DropPalletePolicyTable[0..5]` | INT | **RW** | where each pallet goes: `0` left, anything else right. Indexed by the pallet number minus 1 |
| `Main.ArmController` | — | **RW** | 116 variables. Use only: `ReadPosition.Position`, `Power.Status`, `Busy`, `StepError`, `Jog.Error`, `MoveAbsolute.Error`, `AxisInterrupt.Error`, `AxisContinue.Error`. **Write nothing here** — see §5 |
| `Main.ConveyorController` | — | **RW** | 115; the same, without `MoveAbsolute.Error`. **Do not write** |
| `Main.RFID_Controller` | — | **RW** | 21; the reader's state. **Do not write** |

All four commands are written with `TRUE`; the PLC sets them back to `FALSE`
itself once it has consumed them. The HMI does not have to clear them.

### 2.1b `HMI` — the command layer (106 variables, ReadWrite)

The program **all** manual commands pass through: jog, power, stop, reset,
absolute and relative movement, RFID, the analog outputs, the Start button, the
colour counters, the current colour, the conveyor distance.

What each flag means, what disables it and what the PLC does when you raise it
are in **`HMI-CONTEXT.md`**, next to this. Not repeated here.

### 2.2 `Main.Layout` — the state of the cell (99 variables)

Published `ReadWrite`, but **the HMI must not write to it**. It is the model kept
in step with the machine by the movement methods in the PLC; a write from outside
desynchronises it silently, and the arm ends up confidently making the wrong move.

| variable | type | what it is |
|---|---|---|
| `Layout.Rows[R]._count` | INT | how many pallets in column `R` |
| `Layout.Rows[R]._pallets_id[0..5]` | INT | the `VirtualId`s, **`[0]` = at the front**. Valid only up to `_count - 1`; the rest are `-1` |
| `Layout.Rows[R]._capacity` | INT | 6, the column's capacity |
| `Layout.IsAtFront[R]` | BOOL | the pallet at the front of a side column is **out**, held by the pullers. See §4 |
| `Layout.InGripper` | INT | the `VirtualId` in the gripper, `-1` = empty |
| `Layout.InVacuum` | ENUM_ObjectType | the object on the vacuum, `Missing` = empty |
| `Layout.PalletCount` | INT | how many `Pool` entries are in use |
| `Layout.DroppedCount[R]` | INT | objects dropped into the side bin `R` |
| `Layout.Pool[0..5]._isValid` | BOOL | the entry is in use |
| `Layout.Pool[0..5]._virtualId` | INT | its own id (= the index) |
| `Layout.Pool[0..5]._realId` | INT | the id read by RFID; `0` if it was never read. **Not a key** |
| `Layout.Pool[0..5]._objectTypes[0..3]` | ENUM_ObjectType | what sits in each of the 4 slots |
| `Layout.Pool[0..5]._objectColorsStr[0..3]` | STRING(80) | the same, as text ready to display |

`R` takes the values `-1`, `0`, `1`. `Rows[0]` **is the belt** — there is no
separate structure for the conveyor.

The underscored names are correct and intentional: OPC UA publishes **variables**,
not properties. `Count`, `Capacity`, `IsValid`, `VirtualId`, `RealId` exist in the
code as a `PROPERTY` and therefore **do not appear** in the address space. Read
the backing fields.

### 2.3 `GVL_Diag.Diag` — why it halted (read-only, 136 variables)

| variable | type | what it is |
|---|---|---|
| `Diag.Active` | BOOL | there is an unacknowledged halt |
| `Diag.Count` | INT | how many valid entries in the history, 32 at most |
| `Diag.Head` | INT | the next write position in the ring buffer |
| `Diag.Cycle` | UDINT | `MainTask`'s cycle counter |
| `Diag.Last.Source` | STRING(60) | `'FB_ArmController.MoveToPosition'` — what halted |
| `Diag.Last.Step` | INT | at which step |
| `Diag.Last.Code` | ENUM_Halt | why; see §3 |
| `Diag.Last.Cycle` | UDINT | in which cycle |
| `Diag.History[0..31].{Source, Step, Code, Cycle}` | | ring buffer, the same fields |

The history is circular: the most recent entry is at `(Head - 1) MOD 32`, and
`Count` entries going back from there are valid.

### 2.5 `IOs` — the process image (78 variables)

49 are read-only, **29 are writable** — all the `%Q` outputs. The dialog gives
them access by direction, and that is how they stayed. They are: `Arm_Extend_Cmd`,
`Arm_Retract_Cmd`, `Gripper_Close_Cmd`, `Vacuum_Cmd`, `Puller_Extend_Cmd`,
`Puller_Retract_Cmd`, `Storage_Gates_Top_Retract_Cmd`,
`Storage_Gates_Bottom_Retract_Cmd`, `AO1`, `AO2`, `RFID_Command`,
`RFID_Address`, `RFID_Block_Number`, `RFID_Write_Byte_0..7`, `DO02`, `DO03`,
`DO11`..`DO16`.

That makes the **Pneumatic page fully reproducible** and also opens up RFID
writing. The price is in §5: you command the pneumatics directly, over any
sequence logic, and with no watchdog on the link.

| group | variables |
|---|---|
| arm | `Arm_Extended`, `Arm_Retracted`, `Arm_Extend_Cmd`, `Arm_Retract_Cmd` |
| gripper / vacuum | `Gripper_Closed`, `Vacuum_Detected`, `Gripper_Close_Cmd`, `Vacuum_Cmd` |
| pullers | `Puller_{Left,Right}_{Extended,Retracted}`, `Puller_{Extend,Retract}_Cmd` |
| storage gates | `Storage_Gate_Top_{Forward,Backward}_Retracted`, `Storage_Gate_Bottom_{Left,Right}_Retracted`, `Storage_Gates_{Top,Bottom}_Retract_Cmd` |
| pallet presence | `Exist_{Forward,Bacward}_{Near,Far}` |
| general | `Air_Presure_Ok`, `Storage_Not_Empty`, `Button_Start` |
| **belt position** | `Distance_Center_1`, `Distance_Center_2` (BYTE) |
| colour sensor | `Red`, `Green`, `Cyan`, `Gray`, `Orange`, `White`, `Black` |
| analog | `AI1`..`AI4`, `AO1`, `AO2` (INT) |
| RFID state | `RFID_Present`, `RFID_Exist_Tag`, `RFID_Ready_Flag`, `RFID_Error`, `RFID_Alarm_1/2`, `RFID_Antenna_Enabled`, `RFID_Status_Byte`, `RFID_Signal_Level` |
| RFID data | `RFID_Read_Byte_0..7`, `RFID_Write_Byte_0..7`, `RFID_Command`, `RFID_Address`, `RFID_Block_Number` |
| spare outputs | `DO02`, `DO03`, `DO11`..`DO16` |

The `*_Cmd` commands are **read** — the Pneumatic page shows the state of each
solenoid valve — but cannot be written.

The belt position is composed as in `FB_ConveyorController.GetCenterDistance`:

```
distance = Distance_Center_1 * 256 + Distance_Center_2
```

`Exist_Bacward_Near` is spelled that way in the project.

## 3. The enums, with values

An OPC UA client may deliver numbers instead of names.

```
ENUM_Region      Left=-1, Center=0, Right=1

ENUM_ObjectType  Unknown=0, Missing=1, NoColor=2, Red=3, Green=4,
                 Cyan=5, Gray=6, Orange=7, White=8, Black=9

ENUM_PalletSlot  Invalid=-1, FirstRowRight=0, FirstRowLeft=1,
                 SecondRowLeft=2, SecondRowRight=3

ENUM_Halt        H_NONE=0, H_NO_PULLERS=-1, H_GRIPPER_SHUT=-2,
                 H_INVALID_ARG=-10, H_POOL_FULL=-14, H_TIMEOUT=-20,
                 H_DRIVE_ERROR=-30
```

`Unknown` means "the pallet exists but has not been scanned yet", `Missing`
means "empty slot". They are not the same thing and are not drawn the same way.

**The layout of the 4 slots on a pallet** (the indices in `_objectTypes`):

```
   2 | 3      <- the back row  (SecondRowLeft, SecondRowRight)
  ---+---
   1 | 0      <- the front row (FirstRowLeft,  FirstRowRight)
```

## 4. How the cell is drawn

For each column `R` in `{-1, 0, 1}`:

```
n = Layout.Rows[R]._count
for i from 0 to n-1:
    id  = Layout.Rows[R]._pallets_id[i]     // i = 0 is at the front
    obj = Layout.Pool[id]._objectTypes[0..3]
```

The arm: `Layout.InGripper >= 0` means it holds the pallet with that id — draw it
in the gripper, not in the column; it has already been taken out of the queue.
`Layout.InVacuum <> Missing` means it holds an object of that colour.

`IsAtFront[-1]` and `IsAtFront[1]`: the pallet at the front of a side column is
**out**, held by the pullers. While it is out, the arm can take pieces from it
(from the back row only, slots 2 and 3) or lift it back. When the pullers retract,
the pallet is drawn into the row and **can no longer come back** — draw it
differently, it is a difference the operator has to see.

The pullers are **a single command for both sides**, so both flags go out
together. `IsAtFront[0]` means nothing — the belt has no pullers.

## 5. What can be written, and what you are allowed to write

They are not the same thing. The configuration publishes **509 writable
variables**; the HMI has to write **126**.

### Write freely

| what | how many | for |
|---|---|---|
| all of `HMI` | 106 | every manual command — jog, power, stop, reset, movements, RFID, Start, analog outputs |
| `Main.StartCommand`, `ResetCommand`, `PauseCommand`, `EndStepPauseCommand` | 4 | the cycle commands |
| `Main.DropObjectPolicyTable[0..9]` | 10 | the sorting policy per colour |
| `Main.DropPalletePolicyTable[0..5]` | 6 | where each pallet goes |

The flags in `HMI` are **levels, not pulses**: the HMI clears them, except for
`ArmStop`, `ConveyorStop`, `ArmReset`, `ConveyorReset`. The full list, and what
happens if you leave them raised — in `HMI-CONTEXT.md` §4.

### Do not write, even though you can

| what | how many | what you break |
|---|---|---|
| `Main.Layout` | 99 | you desynchronise the machine model, silently. All the bookkeeping in the PLC assumes that only the movement methods touch it |
| `Main.ArmController`, `ConveyorController`, `RFID_Controller` | 252 | you write straight into the motion blocks: `Power.Enable`, `Jog.JogForward`, `MoveAbsolute.Execute`. You bypass the logic in `HMI`, travel limits included |
| `Main.HaltStep`, `PalletDropRegion`, `ConfirmCycleEnd` | 3 | task variables; you would be fighting `MainTask` |
| the 29 outputs in `IOs` | 29 | you command the pneumatics over the sequence. **Only** if you build the Pneumatic page, and only while `Main.Run` is false |

### Two rules that belong to the HMI, not to the PLC

- **Block manual commands while `Main.Run` is true.** The PLC ignores them
  anyway — `HMI.impl` calls the command methods only while the cell is not
  running — so a live button would look broken.
- **There is no watchdog on the link.** If the session drops with
  `HMI.ArmJogRight` raised, the arm runs to `JogMax`. Send `FALSE` on release, on
  loss of focus and on close; on disconnection, try to drop every flag before
  giving up.

## 6. Polling

Two nodes are heavy and have no business in the refresh loop:

- `Diag.History` — 32 × `STRING(60)`, ~2 KB. Read it when the diagnostics panel
  opens. What belongs in the loop is `Diag.Active`, `Diag.Last.*`, `Diag.Count`.
- `Layout.Pool[*]._objectColorsStr` — ~1.9 KB, 88% of the whole `Layout`
  structure. If the HMI translates `ENUM_ObjectType` into names itself (§3), the
  rest of the model fits in ~260 bytes.

## 7. What is NOT published

Nothing the HMI needs. What is missing, is missing because it is not needed:

| what | why |
|---|---|
| `Main.MainController` | taken out — 233 variables no page reads; the colour arrives ready-made in `HMI.CurrentObjectColor` |
| `Main.StorageController` | taken out — unused by the HMI |
| the other step variables | `ScanAndDropAllObjectsStep`, `PickAndPlaceObjectStep`, `PickAndPlacePalletStep`, `ResetStep` — only if you want progress within sub-sequences |
| the axis position as a separate value | it arrives in `Main.ArmController.ReadPosition.Position` |

**Left published for nothing**, if you want to tidy up next time you open the
dialog: `Main.ObjectPriorities` (10), `Main.ConfirmCycleEnd`, `Main.ValueFromRFID`,
`Main.HaltStep`, `Main.PalletDropRegion`. That is 14 variables, they bother
nobody — just do not bind anything to them.

## 8. To be decided before going much further

**`GVL_Config` is read-only, but the comment at the head of it says the positions
are re-taught from the HMI with the cell running** — `Main` copies the values into
the controllers every cycle, so a change takes effect from the next cycle, with no
restart and no download. With read-only access, that cannot be done.

If you want re-teaching from the HMI: `GVL_Config.Arm` and `.Conveyor` move to
**ReadWrite** in the dialog. `GVL_Config.Main` stays Read — `SlotOrder` is
`VAR_GLOBAL CONSTANT`.

The consequence to weigh: `TravelMin` / `TravelMax` / `JogMin` / `JogMax` become
writable too, that is the limits guarding the travel. A wrong value sent over the
network drives the arm into a mechanical stop. Either the HMI limits what it
sends, or the positions to be taught move into a structure separate from the
limits and only that one is published writable.

## 9. How to check the configuration

With the project open in the IDE and the daemon running:

```bash
python "E:\Mecatronica\_AI Workplace\_AI Tools\cds\cds.py" session
```

Regenerating the symbol file is asked of the daemon with the `symbols` operation
(~4 s). `build` does **not** rewrite it. From outside the IDE, with the project
closed, `job_gencode.py` in `_AI Workplace\Software v13\hmi-extract\` does the
same.

After regeneration, the truth is in `Software v13.Device.Application.xml` — the
number of variables, the access of each one, and the types.
